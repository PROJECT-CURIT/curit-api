# QR 주문 아키텍처

## 선택한 구조

```text
상품별 QR
  → curit-qr-web /q/{opaqueToken}
  → curit-api GET /api/v1/qr/{opaqueToken}
  → 전시 매장·작가·상품·실시간 재고 조회
  → 주문 요청
  → 서버 가격으로 pending 주문 생성
  → Toss v2 결제 인증·서버 승인
  → 재고 원자적 차감 + paid 전환 + 정산 원장 생성
```

QR은 상품 마스터가 아니라 `특정 매장에 배치된 특정 상품`을 가리킵니다. 그래야 같은 굿즈라도 매장별 재고, QR 조회, 주문, 매출과 정산을 구분할 수 있습니다.

QR 웹은 브라우저에서 만든 무작위 익명 식별자를 조회 요청에 함께 보냅니다. 서버는 원문을 저장하지 않고 SHA-256 해시만 보관하며, 상품·해시·한국 날짜 조합을 고유키로 사용해 같은 사람이 새로고침해도 하루 한 번만 집계합니다. IP 주소와 사용자 에이전트는 수집하지 않습니다.

## 저장소 분리 이유

- `curit-qr-web`: 앱 설치 없이 방문객이 접근하는 모바일 웹
- `curit-api`: QR 웹과 모바일 앱이 공유하는 주문·재고·정산의 기준
- `curit-mobile`: 매장 운영자와 크리에이터용 앱

프런트엔드 두 개를 한 저장소로 합치지 않으면 배포 주기와 사용자 환경을 독립적으로 관리할 수 있습니다. 대신 데이터 규칙은 API 하나에서만 관리해야 합니다.

## 운영 DB

거래 테이블에는 전시 상품 snapshot과 가격·재고를 함께 저장합니다. 주문 순간 snapshot을 복사해 이후 작품 설명이 바뀌어도 거래 당시 내역을 보존합니다. 크리에이터, 작품, 매장, 협업, 주문, 정산은 별도 테이블로 정규화하며 앱 사용자는 RLS로 자신의 프로젝트·매장·정산 데이터만 수정할 수 있습니다.

PostgreSQL에서는 `UPDATE ... WHERE stock >= quantity RETURNING`으로 재고를 한 번에 검사·차감합니다. 이 경계가 없으면 두 방문객이 마지막 재고를 동시에 구매할 수 있습니다.

## 결제·정산 경계

- 클라이언트가 보낸 가격은 사용하지 않고 DB의 현재 가격으로 주문을 생성합니다.
- Toss 인증 성공 후에도 서버가 주문번호와 금액을 다시 검증합니다.
- 승인 이후 재고가 부족하면 결제를 즉시 자동 취소합니다.
- 정산 원장은 생성하지만 실제 계좌 송금은 사업자·세무·계약 절차가 확정된 뒤 지급대행 또는 관리자 승인으로 연결합니다.
- QR 방문객의 휴대폰 입력은 주문 연락처 확인이며 통신사 본인인증으로 표현하지 않습니다.
