# QR 주문 아키텍처

## 선택한 구조

```text
상품별 QR
  → curit-qr-web /q/{opaqueToken}
  → curit-api GET /api/v1/qr/{opaqueToken}
  → 전시 매장·작가·상품·실시간 재고 조회
  → 주문 요청
  → 서버 가격 재계산 + 재고 원자적 차감
  → 결제 승인(현재 데모, 운영 Toss v2)
  → 주문·정산 데이터 저장
```

QR은 상품 마스터가 아니라 `특정 매장에 배치된 특정 상품`을 가리킵니다. 그래야 같은 굿즈라도 매장별 재고, QR 조회, 주문, 매출과 정산을 구분할 수 있습니다.

## 저장소 분리 이유

- `curit-qr-web`: 앱 설치 없이 방문객이 접근하는 모바일 웹
- `curit-api`: QR 웹과 모바일 앱이 공유하는 주문·재고·정산의 기준
- `curit-mobile`: 매장 운영자와 크리에이터용 앱

프런트엔드 두 개를 한 저장소로 합치지 않으면 배포 주기와 사용자 환경을 독립적으로 관리할 수 있습니다. 대신 데이터 규칙은 API 하나에서만 관리해야 합니다.

## 운영 DB

현재 마이그레이션은 빠른 PoC를 위해 전시 상품 snapshot과 가격·재고를 함께 저장합니다. 주문 순간 snapshot을 복사해 이후 작품 설명이 바뀌어도 거래 당시 내역을 보존합니다. 서비스 검증 후에는 크리에이터, 작품, 매장, 전시 요청, 배치 상품, 재고, 주문, 정산 테이블로 정규화합니다.

PostgreSQL에서는 `UPDATE ... WHERE stock >= quantity RETURNING`으로 재고를 한 번에 검사·차감합니다. 이 경계가 없으면 두 방문객이 마지막 재고를 동시에 구매할 수 있습니다.

## 의도적으로 구현하지 않은 것

- 실결제: 상점 계약과 키가 없으므로 성공을 위조하지 않음
- 통신사 본인인증: 주문 연락처 확인만으로 충분한지 PoC 후 결정
- 자동 정산: 판매자·매장·플랫폼의 법적 계약과 수수료 정책 확정 후 구현
